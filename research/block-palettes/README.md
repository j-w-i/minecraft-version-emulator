# Per-version block palettes

One file per Minecraft Java version, recording the set of **block names that version's own client
registers**. A version check uses these to ask "could this block have existed in version X?" — a name
that is absent is a name that version never had.

Generated by `scripts/extract-block-palette.py` (standard library only). Reproduce everything with:

```powershell
python scripts\extract-block-palette.py --self-check
python scripts\extract-block-palette.py --all --out-dir research\block-palettes
python scripts\extract-block-palette.py --inspect 1.6.4          # structural report, writes nothing
```

The run refuses to emit anything unless the self-check passes. The self-check has two parts:

1. **Beta 1.7.3 must reproduce the 83-name set in `research/beta173-block-palette.json` exactly, in
   order.** That file is parent-reviewed (`ACCEPTED_FOR_VERSION_CHECKS`) and remains the authoritative
   Beta 1.7.3 artifact; `block-palettes/b1_7_3.json` is this tool's byte-identical re-derivation of the
   same name list, emitted here only so every version has a file in one place with one schema.
2. **Beta 1.8.1 must reproduce a 92-name list that was read by hand from the registry class before this
   tool existed.** This exists to catch a silent change in registry identification or naming convention,
   which the Beta 1.7.3 check alone would not catch, since Beta 1.7.3 is the easy case.

`MOJANG` means the digest comes from Mojang's own version metadata. `ARCHIVE_VERIFIED` means Mojang never
published that build to the launcher manifest, so the digest comes from an independently published
per-version metadata document and the jar itself is archive-hosted; the download URL is inside that
document, so the digest and the artifact are not the same source. Every jar's SHA-1 **and** byte length
are checked before a class file is read; a mismatch aborts the version.

## The versions that could NOT be done

**Alpha v1.1.2_01, Infdev 20100420 and Infdev 20100611 have no block palette, and that is a finding,
not a gap in effort.** These builds do not attach a name to a block at registration, so the name set
does not exist inside the jar in any form. The concrete evidence, all of it reproducible:

- The block registry is found structurally in every one of them — Alpha `ly.class` (80 objects
  constructed, 36 subclasses), Infdev 20100420 `net/minecraft/a/a/b/x.class` (72 constructed,
  22 subclasses), Infdev 20100611 `net/minecraft/a/a/b/y.class` (75 constructed, 24 subclasses). The
  block class is identified too: Alpha `bb.class`, which declares an instance `Ljava/lang/String;`
  field `a` and a `(Ljava/lang/String;FF)V` constructor with a name getter — i.e. the structure for a
  per-block name exists.
- **The registry never supplies one.** The Alpha registry's `<clinit>` constructs blocks with arguments
  that are not names, and it loads exactly nine strings in total. All nine are *material* names
  (`stone`, `wood`, `gravel`, `grass`, `stone`, `stone`, `stone`, `cloth`, `sand`); `dirt`, `bedrock`,
  `water` and `lava` — blocks Alpha certainly had — do not appear as strings anywhere in the jar.
- A scan of **every string constant in every class** of the Alpha jar (474 classes, 878 distinct
  strings) finds no `tile.*` key, no `tile.<name>.name`, and no human-readable block name. The same is
  true for both Infdev jars. Infdev 20100420 and 20100611 load the *same nine* material strings.
- Those display names live in a **translation map loaded from an external `.lang` file at runtime**
  (`fr`/`it` in Alpha), which is not in the client jar. Alpha's jar has no `lang/` directory at all.

Consequence for the mod: for Alpha and Infdev the palette check must treat the block-name set as
UNKNOWN. Do not read `blockNames: []` as "this version had no blocks".

## How the registry and the names are found

Nothing identifies a class by guessing a name, which is what defeated the earlier Alpha attempt (it
probed for `stone`/`dirt`/`bedrock`/`grass` and scored 2 of 4, landing on the material class).

**Registry identification.** Every class's static initialiser is walked with a complete opcode-width
table and a stack-slot simulation of the object-construction pattern (`new X; dup; …; invokespecial
X.<init>`). The registry is the `<clinit>` that constructs the most **distinct classes**. That
distinction is load-bearing: ranking by raw construction count picks the *item* registry on five of the
ten versions (Beta 1.7.3: item registry `gm` 107 objects, block registry `uu` 113 objects, but 32 vs 79
distinct classes). Block registries construct 52–126 distinct classes here; item registries 14–53.

**Name attachment.** Three mechanisms occur, and the tool reports which one it found:

| Mechanism | Versions | How the name is attached |
|---|---|---|
| `plain` | Beta 1.7.3, Beta 1.8.1, Beta 1.9-pre3, 1.0.0, 1.1, 1.2.5 | the name is a lowerCamelCase string constant loaded in the registry's `<clinit>` |
| `setter` | 1.6.4 | a chained `(String) -> <registry type>` method is called once per block; the name is the string constant loaded immediately before the call |
| `none` | Alpha v1.1.2_01, Infdev 20100420, Infdev 20100611 | nothing is attached; the jar contains no block-name strings |

For 1.6.4 two such setter families exist. The tool does not assume which is which: it takes the family
covering the most blocks as the primary set (142 names, the pre-flattening identifiers such as
`oreGold`) and records the other family's non-duplicate names as `aliasNames` (71 names, the
post-flattening texture names such as `gold_ore`). The classification is independently confirmed
against the client's own `assets/minecraft/lang/en_US.lang`: 128 of its 129 `tile.<name>.name` keys are
in the primary set, and the one that is not is `oreRuby`, a language entry for a block that was never
registered.

## Controls actually run

Per version, from the jar and its own names:

- **positive** — blocks the version certainly had must be present. Names are the versions' own
  spellings, which differ across eras: Beta 1.8's stone-brick stairs are `stairsStoneBrickSmooth` and
  its iron bars are `fenceIron`, not `stoneStairs`/`ironFence`; Beta 1.9-prerelease-3's End Portal
  frame is `airPortalFrame`, renamed `endPortalFrame` by 1.0.0; 1.6.4's ore blocks are `oreGold` etc.
  Getting an era's spelling wrong makes a correct extraction look broken.
- **negative** — blocks the version certainly could not have had must be absent. Beta 1.8.1 is checked
  against the Nether (`hellrock`, `hellsand`, `lightgem`) and the 1.0.0 additions; 1.0.0/1.1 against the
  redstone lamp, wood slabs, cocoa, tripwire, command block, beacon, quartz and hopper; 1.6.4 against
  the 1.7+ names (`stone_granite`, `prismarine`, …) and the never-released `oreRuby`.
- **parse completeness** — the count of class files parsed to their exact last byte. Every palette here
  reports `classCount == classesParsedToExactEnd` with zero parse failures and zero unsupported constant
  pool tags. A partial parse would make the constant pool read untrustworthy, so it is an error, not a
  warning.

Alpha/Infdev controls report `passed: false` **by design**: their positive controls cannot be satisfied
because no names exist to satisfy them, and the file says so in `nameRecovery.note`. Do not treat those
three files as failed extractions; treat them as a documented negative result.

## Known limitations

- **Numeric ids are not paired with names.** Deliberately: a positional id/name pairing is how an
  earlier artifact went wrong. Where ids appear in the checks they come from this project's separate,
  reviewed evidence.
- **`blockNames` is a name set, not an inventory.** In 1.6.4 the union of `blockNames` and
  `aliasNames` is the set of names the client knows; the same block can appear under two names.
- **The "plain lowerCamelCase" filter is a heuristic and is the weakest step.** It is why the setter
  mechanism is tested first on later jars: in a 1.6.4 registry the plain filter also matches texture
  names such as `planks` and `cobblestone`, so testing it first produced a 151-name mixture.
- **Over-inclusion is possible in principle; under-inclusion is what matters.** A name wrongly present
  weakens a version check; a block wrongly absent would only ever be reported UNKNOWN by the consumer,
  because an absent name is not treated as proof of non-existence unless the palette is trusted. The
  palettes here are trusted only where the controls above passed.
- **Beta 1.9-pre3's digest is `ARCHIVE_VERIFIED`, not Mojang.** Mojang never shipped that build through
  the launcher; the SHA-1 comes from an independently published metadata document that
  [minecraft.wiki's version page](https://minecraft.wiki/w/Java_Edition_Beta_1.9_Prerelease_3) links
  for the same file. There are two Beta 1.9 Prerelease 3 clients (original `-1350`, reupload `-1402`);
  this is the **original**, `-1350`.
- `b1_7_3.json` in this directory and `research/beta173-block-palette.json` hold the same 83 names. The
  latter is the reviewed one and should be preferred where only one may be read.

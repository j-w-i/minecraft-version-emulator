# Adding a historical version — the exact, ordered checklist

Derived by tracing three already-declared versions end to end, because between them they exercise every
mechanism this repository has:

| worked example | shape | revisions | why it is the example |
| --- | --- | --- | --- |
| `historical_experience:release_1_6_4` | `terrainOnly(...)` | 3 (`0`, `_cave_fix`, `_no_modern_content`) | a terrain-only version: terrain inherits an upstream Moderner Beta preset, simulation rules are deliberately `unmodified` |
| `historical_experience:beta_1_7_3` | hand-written entry | 11 (`0` … `_content_preview_10`) | a version whose generation content was corrected over ten append-only revisions |
| `historical_experience:beta_1_8_1` | hand-written entry | 3 (`0`, `_cave_fix`, `_no_modern_content`) | a version with its own upstream foundation and its own researched simulation rules |

Everything below was read from the current tree, not from the prose. Where a document disagrees with the code,
the disagreement is recorded in §7 rather than smoothed over.

Line citations are against the working tree at the time of writing (no commit after `3bed0a8`). Any symbol in
this document can be found by name (`HistoricalGameplayTweaks.BEFORE_BETA_1_8`,
`HistoricalStructureRules.RULES`, `HistoricalVersions` static block, …), which is the durable anchor: other
work in this repository is editing those files concurrently and a line number can move without the invariant
changing.

---

## 1. What a declared version actually touches

A "version" is one entry in `src/main/java/net/historicalexperience/version/HistoricalVersions.java`. Every
other artefact is either (a) *derived* from that registry and needs no change, or (b) a **separate table that
still lists versions by hand** and therefore must be edited. The two are not distinguishable by looking at the
registry, which is why later implementation work keeps missing (b).

| # | artefact | who owns it | new version needs |
| --- | --- | --- | --- |
| 1 | registry entry (`HistoricalVersions.java:56-339`) | hand-written | **edit** |
| 2 | settings preset JSON per revision | hand-written (one file per alias) | **new files** |
| 3 | world preset JSON per revision | generated by `scripts/generate-1211-world-presets.py` | **regenerate** |
| 4 | `minecraft:normal` tag | generated by the same script | **regenerate** |
| 5 | structure rule per version | `generation/HistoricalStructureRules.java:143-188` | **edit** |
| 6 | block-introduction chronology | `generation/HistoricalBlockAvailability.java:60-71` + its generator script | **edit + regenerate** |
| 7 | pre-Beta-1.8 gate set | `gameplay/HistoricalGameplayTweaks.java:41-46` | **edit** (only for a version older than Beta 1.8) |
| 8 | GUI catalogue | `version/HistoricalVersionCatalogue.java:200-255` | **edit** |
| 9 | lang keys | `assets/historical_experience/lang/en_us.json` | cosmetic; no test |
| 10 | marker list | `HistoricalMarker.java:146-147` | **derived — nothing** |
| 11 | profile/binding table | `profile/HistoricalProfiles.java:97-129` | **derived — nothing** |
| 12 | spawn / loot / food / ore / exclusion tables | `gameplay/*`, `generation/*` | **derived — nothing** (but new *constants* are needed if the research values differ) |
| 13 | screens (`client/version/*`) | reads the catalogue | **nothing** |
| 14 | 6 test files with pinned counts/lists | `src/test/**` | **edit** |

### The declaration point, quoted

```java
// HistoricalVersions.java:21-25
 * <p><b>This is the single place a version is declared.</b> Adding a version means adding one entry
 * here, plus the two resource files its revisions need; every subsystem - markers, profile bindings,
 * generation-content exclusions, ore placement, natural spawning, mob drops, experience, sprinting and
 * hunger - reads its data through this registry instead of keeping its own table. The registry test
 * asserts that invariant, so a new version cannot quietly be declared in one subsystem only.
```

That comment is **true for the twelve names it lists and false for three tables it does not name** —
`HistoricalStructureRules.RULES`, `HistoricalGameplayTweaks.BEFORE_BETA_1_8` and
`HistoricalBlockAvailability.CHRONOLOGY` each still enumerate versions (see §7.1).

### The trace, in one line each

* `HistoricalVersions` static block builds the list and runs a duplicate-id/duplicate-alias self-check
  (`HistoricalVersions.java:341-357`).
* `HistoricalProfiles` derives one canonical profile per version and one binding per revision from that list
  (`HistoricalProfiles.java:100-129`), and each binding must inherit `moderner_beta:*`
  (`HistoricalProfiles.java:162-167`).
* `HistoricalMarker.HISTORICAL_PRESET_IDS` is the registry's alias list, verbatim
  (`HistoricalMarker.java:146-147`), so no marker edit is ever needed.
* A world is created by selecting the world preset `historical_experience:<alias>` —
  `level-type=historical_experience:beta_1_7_3` (`scripts/generate-1211-world-presets.py:104`) — and only
  presets listed in `data/minecraft/tags/worldgen/world_preset/normal.json` reach the create-world list
  (`scripts/generate-1211-world-presets.py:98-100`).
* A world persists the **alias**, not the version id (`world/metadata/HistoricalMetadata.java:26-28`,
  `MetadataJson.java:28-34`), and an alias the build does not declare makes the world `Unreadable`
  (`docs/GUI-REDESIGN.md:51-53`).

## 2. The checklist

Steps 1–17 are "declare one new version". Steps R1–R6 are "add a further revision to a version that already
exists" and are the normal path once a version is live.

### Step 1 — pick the upstream foundation, and prove it exists

**File:** no edit. **Input:** `.upstream/moderner-beta/src/main/java/mod/bluestaggo/modernerbeta/settings/ModernBetaSettingsPresets.java`.

The `foundation` of every revision must be a real Moderner Beta settings-preset id, because
`HistoricalProfiles.registerBinding` throws otherwise (`HistoricalProfiles.java:162-167`):

```java
        if (!binding.terrainPreset().value().startsWith("moderner_beta:")) {
            throw new IllegalStateException(
                "generation binding " + key + " records terrain foundation "
                    + binding.terrainPreset() + ", which is not a Moderner Beta preset; terrain must "
                    + "always inherit from the pinned upstream foundation");
        }
```

Check the id against the pinned dependency, not against a guess. Alpha is the sharp example: the pinned
Moderner Beta has **one** Alpha preset —

```java
// .upstream/moderner-beta/.../ModernBetaSettingsPresets.java:11
    public static final ResourceKey<ModernBetaSettingsPreset> ALPHA_1_1_2_01 = keyOf("alpha");
```

— so *Alpha 1.2.0 must inherit `moderner_beta:alpha`*, the same foundation the Alpha v1.1.2_01 profile already
uses. Sharing a foundation across two versions is legal: the binding table is keyed by the owned alias, not by
the foundation (`HistoricalProfiles.java:152`), and `GenerationBindingTest` only asserts the recorded
foundation is one its owning version declares (`GenerationBindingTest.java:158-164`).

**Breaks if missed:** a foundation that is not a `moderner_beta:` id throws `IllegalStateException` during
`HistoricalProfiles` class initialisation — every test and every server start fails at once. A foundation that
exists but is the wrong era silently generates the wrong terrain while the metadata says otherwise (see §6.4).

### Step 2 — declare the version in the registry

**File:** `src/main/java/net/historicalexperience/version/HistoricalVersions.java`, inside the `static { }`
block. Use the helper that matches the version's state; do not hand-write a `HistoricalVersion` unless the
version needs restrictions from its own revision 0 (as Beta 1.7.3 and Beta 1.8.1 do).

Terrain-only version with no researched simulation rules — the template is Release 1.6.4:

```java
// HistoricalVersions.java:263-266
        versions.add(terrainOnly(
            "historical_experience:release_1_6_4", "Release 1.6.4", "release",
            chronology(ERA_RELEASE, 1, 6, 4), "moderner_beta:release_1_6_4",
            HistoricalFeatureExclusions.RELEASE_1_2_5_WITHOUT_MODERN_VANILLA_FEATURES));
```

Terrain-only version with researched simulation rules — the template is Alpha v1.1.2_01:

```java
// HistoricalVersions.java:312-313
        versions.add(alphaTerrainOnly(
            "historical_experience:alpha", "Alpha v1.1.2_01", "moderner_beta:alpha"));
```

`alphaTerrainOnly` is **not reusable for a second Alpha version**: it hard-codes the era and
`ERA_ALPHA + 112` (`HistoricalVersions.java:460-461`), so a second call would collide on chronology and fail
`HistoricalVersionsTest.registryDeclaresDistinctVersions` (`HistoricalVersionsTest.java:44-49`).
Call `terrainOnlyWithRules(...)` directly instead (see the worked example in §4).

**Breaks if missed:** nothing exists, nothing resolves. The record's own constructor refuses the cheap
mistakes (§3), and a duplicate id or alias is refused by the registry self-check:

```java
// HistoricalVersions.java:346-357
            HistoricalVersion previous = byId.put(version.id(), version);
            if (previous != null) {
                throw new IllegalStateException("duplicate version id " + version.id());
            }
            ...
                HistoricalVersion owner = byAlias.put(revision.alias(), version);
                if (owner != null) {
                    throw new IllegalStateException("recipe alias " + revision.alias()
                        + " is declared by both " + owner.id() + " and " + version.id());
                }
```

### Step 3 — supply the research constants the rules refer to

**Files (only if the values differ from every existing constant):**
`gameplay/HistoricalSpawnRules.java`, `gameplay/HistoricalFoodRules.java`,
`gameplay/HistoricalLootRules.java`, `generation/BetaOreRules.java`.

`VersionRules` holds four maps/sets and they are **not** defaulted for you: an empty `allowedNaturalSpawns`
with `restrictsSpawns=false`, an empty `foodHealPoints`, an empty `mobDrops` and an empty `orePopulation` all
mean "leave the modern behaviour alone", which is the honest state for unresearched data
(`HistoricalVersions.java:474-494`, `HistoricalVersion.java:150-208`).

```java
// HistoricalVersions.java:483-494 — the deliberate "not researched yet" shape
    private static VersionRules preBetaRules(String evidence) {
        return new VersionRules(
            false,                   // spawns NOT restricted: unresearched, so modern spawning is left alone
            java.util.Set.of(),      // and therefore no allowed set may be named, which the record enforces
            java.util.Map.of(),      // drops not researched
            java.util.Map.of(),      // food heals not researched
            false,                   // no experience, inferred by monotonicity from Beta 1.7.3/1.8.1
            false,                   // no sprinting, same inference
            false,                   // no hunger, same inference
            false,                   // no structures: mineshafts, villages and strongholds arrive in Beta 1.8
            evidence);
    }
```

The existing constants are keyed by *the version that was researched*, so reuse is a research claim, not a
mechanical act: `ALPHA_1_1_2_MOBS` is "the ten mobs of Alpha v1.1.2_01" (`HistoricalSpawnRules.java:96-107`),
and Alpha 1.2.0 is the Halloween Update, so copying that set would assert something unmeasured. Declare the
gap instead.

**Breaks if missed:** a named-but-undeclared constant is a compile error; a borrowed constant is a plausible
wrong answer that no test catches.

### Step 4 — choose or add the generation-content exclusion lists

**File:** `src/main/java/net/historicalexperience/generation/HistoricalFeatureExclusions.java`.

A revision points at a `List<Exclusion>` constant. The registry resolves the list **from the alias**
(`HistoricalFeatureExclusions.java:412-415`), so the alias is the only wiring:

```java
// HistoricalFeatureExclusions.java:412-415
    public static List<Exclusion> forAlias(String rawAlias) {
        return net.historicalexperience.version.HistoricalVersions.byRevisionAlias(rawAlias)
            .flatMap(version -> version.revisions().stream()
                .filter(revision -> revision.alias().equals(rawAlias))
```

**Append-only rule:** if the new version needs *any* different exclusion, add a **new constant**. Editing an
existing one retroactively changes what every already-generated world on every revision that references it
means. The repository says so at the point of the mistake it corrected:

```java
// HistoricalFeatureExclusions.java:172-176
     * <p>This is a NEW set rather than an addition to {@link #BETA_1_7_3_WITH_REPLACED_ORES}, because
     * revisions 4, 5 and 6 already reference that one and worlds exist on them: adding to it would change
     * what those recorded recipes generate, which is the thing the append-only rule protects.
```

Reuse is safe only when the required set is *identical*; e.g. Alpha v1.2.0 and Alpha v1.1.2_01 both predate
grass, so both may reference `BEFORE_GRASS_EXISTED_WITHOUT_DESERT_WELL`
(`HistoricalFeatureExclusions.java:289-310`).

**Breaks if missed:** no exclusions means modern blocks, plants and features generate and nothing fails —
the failure mode is a world that looks right in a test and wrong in play.

### Step 5 — choose or add the ore population

**File:** `src/main/java/net/historicalexperience/generation/BetaOreRules.java`.
`orePopulation` empty means "vanilla modern ore placement" (`HistoricalVersion.java:144-147`). Only Beta 1.7.3
has researched ores; every other version leaves them modern and says so in its evidence string. Reuse
`BetaOreRules.BETA_1_7_3` only as part of a deliberate "this version's ores were unchanged from 1.7.3"
claim — that is exactly the claim Beta 1.8.1's revisions make (`HistoricalVersions.java:203-229`).

### Step 6 — write one settings preset JSON per revision alias

**Directory:** `src/main/resources/data/historical_experience/moderner_beta/settings_preset/<alias path>.json`.
The file name is the alias with the namespace stripped — and a test derives that path from the registry, so
the file must exist for **every** revision, including revisions whose JSON is byte-identical to a sibling's.

Template (the version-0 file of a terrain-only Release version):

```json
// src/main/resources/data/historical_experience/moderner_beta/settings_preset/release_1_6_4.json:1-22
{
  "chunkSettings": {
    "moderner_beta:preset": "moderner_beta:release_1_6_4",
    "moderner_beta:deepslate_generation": {
      "enabled": false
    },
    "moderner_beta:noise_generator_settings": "moderner_beta:overworld_128",
    "moderner_beta:noise_settings": {
      "height": 128,
      "min_y": 0,
      "size_horizontal": 1,
      "size_vertical": 2
    }
  },
  "biomeSettings": {
    "moderner_beta:preset": "moderner_beta:release_1_6_4"
  },
  "caveBiomeSettings": {
    "moderner_beta:preset": "moderner_beta:release_1_6_4",
    "moderner_beta:provider": "moderner_beta:none"
  }
}
```

The `moderner_beta:preset` value in all three blocks must equal the revision's `foundation` field in the
registry. **No test checks that correspondence** (§6.4) — it is manual discipline.

A revision whose *only* difference is the exclusion list still needs its own file, with identical bytes. That
is the current state of three version families:

```text

06E9F970264E  alpha_no_grass.json

```

The only exception that *must* differ is a revision that changes the cave-biome provider, which is how the
null-biome defect was fixed for the newer versions:

```json
// .../settings_preset/beta_1_7_3_content_preview_6.json:18-22
  "caveBiomeSettings": {
    "moderner_beta:preset": "moderner_beta:beta",
    "moderner_beta:provider": "moderner_beta:single",
    "moderner_beta:single_biome": "moderner_beta:beta_taiga"
```

**Breaks if missed:**
`HistoricalVersionsTest.everyRevisionHasItsResources` fails (`HistoricalVersionsTest.java:110-126`):

```java
                assertNotNull(resource(
                        "/data/historical_experience/moderner_beta/settings_preset/" + path + ".json"),
                    "missing settings preset for " + revision.alias());
```

and a world created on that alias cannot resolve its generator at all.

### Step 7 — produce the world preset JSON per revision

**Directory:** `src/main/resources/data/historical_experience/worldgen/world_preset/<alias path>.json`.

Do **not** hand-write these. `scripts/generate-1211-world-presets.py` writes exactly one per settings preset,
naming the settings alias in **three** places, and it is idempotent:

```python
# scripts/generate-1211-world-presets.py:44-57
    return {
        'dimensions': {
            'minecraft:overworld': {
                'type': 'historical_experience:beta_1_7_3_overworld' if reduced else 'minecraft:overworld',
                'generator': {
                    'type': 'moderner_beta:moderner_beta',
                    'biome_source': {
                        'type': 'moderner_beta:moderner_beta',
                        'cave_provider_settings': settings(),
                        'provider_settings': settings(),
                    },
                    'provider_settings': settings(),
                },
            },
```

The three references are load-bearing — writing fewer leaves a world whose terrain and cave biomes disagree
(`docs/GUI-REDESIGN.md:25-27`), and the test asserts all three agree
(`GenerationBackport1211Test.java:44-52`):

```java
            String alias = generator.getAsJsonObject("provider_settings")
                .get("moderner_beta:preset").getAsString();
            var biomeSource = generator.getAsJsonObject("biome_source");
            assertEquals(alias, biomeSource.getAsJsonObject("provider_settings")
                .get("moderner_beta:preset").getAsString(), id + ": generator and biome source disagree");
            assertEquals(alias, biomeSource.getAsJsonObject("cave_provider_settings")
                .get("moderner_beta:preset").getAsString(), id + ": generator and cave provider disagree");
```

**The dimension type** is referenced once, in the overworld entry, and the script pins the project's single
existing dimension type for every version:

```json
// .../worldgen/world_preset/release_1_6_4.json:2-5
  "dimensions": {
    "minecraft:overworld": {
      "type": "historical_experience:beta_1_7_3_overworld",
```

`src/main/resources/data/historical_experience/dimension_type/beta_1_7_3_overworld.json` is the only dimension
type in the project (`min_y 0`) and is shared by every version; **a new version needs a new dimension type only
if it needs a different level envelope**, in which case the script's hard-coded `type` and the `reduced` flag
(`scripts/generate-1211-world-presets.py:47,93`) both have to learn about it. Note the mismatch recorded in
§7.7.

**Run:** `python scripts/generate-1211-world-presets.py`.

**Breaks if missed:** `HistoricalVersionsTest.everyRevisionHasItsResources` fails on the world preset
(`HistoricalVersionsTest.java:121-123`), and `level-type=historical_experience:<alias>` cannot be selected.

### Step 8 — add the structure rule

**File:** `src/main/java/net/historicalexperience/generation/HistoricalStructureRules.java:143-188`.

Every declared version needs an entry; the table is an **allow-list**, so a missing entry means *nothing* is
suppressed and later structures generate freely (`HistoricalStructureRules.java:240-247`).

```java
// HistoricalStructureRules.java:149-152
        Map.entry("historical_experience:alpha", noStructures("Alpha v1.1.2_01",
            "It has monster rooms, which are features, but no structure-system structure")),
        Map.entry("historical_experience:beta_1_7_3", noStructures("Beta 1.7.3",
            "It has monster rooms, which are features, but no structure-system structure")),
```

Use `noStructures(...)` when the version had no structure-set structure, `allowed(...)` when it had some. The
rule must agree with the registry's `hasStructures` flag:

```java
// src/test/java/net/historicalexperience/generation/HistoricalStructureRulesTest.java:118-126
        for (HistoricalVersion version : HistoricalVersions.all()) {
            boolean ruleForbidsEverything = HistoricalStructureRules.ruleForVersion(version.id())
                .map(rule -> rule.restricts() && rule.allowedStructureIds().isEmpty())
                .orElse(false);
            if (!version.rules().hasStructures()) {
                assertTrue(ruleForbidsEverything,
                    version.id() + " claims to have no structures but declares no rule enforcing it");
            }
        }
```

**Breaks if missed:** `ProfileGenerationRules1211Test.everyDeclaredVersionHasASourcedStructureRule` fails
twice over (`ProfileGenerationRules1211Test.java:78-85`):

```java
            assertTrue(HistoricalStructureRules.ruleForVersion(version.id()).isPresent(),
                version.id() + " has no structure rule, so later structures could generate in it");
        }
        assertEquals(HistoricalVersions.all().size(), HistoricalStructureRules.declaredVersions().size(),
            "the rule table and the version registry disagree about how many profiles exist");
```

### Step 9 — add the version to the block-introduction chronology, then regenerate

**Two files:** `scripts/generate-1211-block-availability.py:26-38` (the source list) and its output
`src/main/java/net/historicalexperience/generation/HistoricalBlockAvailability.java:60-71`.

Insert the id **in registry chronology order** (Alpha 1.2.0 goes after `historical_experience:alpha` and before
`historical_experience:beta_1_7_3`):

```java
// HistoricalBlockAvailability.java:59-71
    /** The declared versions oldest first; a unit test asserts this equals the version registry. */
    public static final List<String> CHRONOLOGY = List.of(
        "historical_experience:infdev_420",
        "historical_experience:infdev_611",
        "historical_experience:alpha",
        "historical_experience:beta_1_7_3",
        ...
        "historical_experience:release_1_6_4"

```

Then run `python scripts/generate-1211-block-availability.py` and commit the regenerated file — the generator
writes the whole file, including this list.

Do **not** add the version to `VERSIONS_WITH_EXTRACTED_PALETTE`
(`HistoricalBlockAvailability.java:85-93`) unless a palette was really extracted for it, and do not add a
palette to `HistoricalBlockPalette.paletteFor` (`HistoricalBlockPalette.java:275-284`), which deliberately
answers `null` for anything but Beta 1.7.3.

**Breaks if missed:** `ProfileGenerationRules1211Test.generatedBlockDatesAgreeWithTheRegistryAndTheReviewedPalettes`
fails on the order equality (`ProfileGenerationRules1211Test.java:175-181`); the Python generator raises
`ValueError` if a timeline row names a version absent from its own `CHRONOLOGY`
(`scripts/generate-1211-block-availability.py:207`, `min(existing[0], version, key=CHRONOLOGY.index)`); and the
generated Java's `introduce(...)` throws at class initialisation if the two lists ever disagree
(`HistoricalBlockAvailability.java:95-99`):

The silent half is worse: `judge` returns `UNKNOWN` for a version it cannot order
(`HistoricalBlockAvailability.java:966-970`), so anachronistic blocks in that version are **not** reported.

### Step 10 — add the version to the pre-Beta-1.8 gate set (only if it predates Beta 1.8)

**File:** `src/main/java/net/historicalexperience/gameplay/HistoricalGameplayTweaks.java:41-46`.

```java
    /** The versions that predate the goal-based mob AI and the Adventure Update's systems. */
    private static final Set<String> BEFORE_BETA_1_8 = Set.of(
        "historical_experience:infdev_420",
        "historical_experience:infdev_611",
        "historical_experience:alpha",
        "historical_experience:beta_1_7_3");
```

This set is used by `appliesTo` (`:143-144`) and by seven public rules that have **no chronology check of
their own**: `swordBlockingEnabled` (`:312-315`), `betaExhaustionCosts` (`:404-406`), `betaGoldenApple`
(`:428-432`), `betaFoodHungerValues` (`:434-438`), `betaRegenerationModel` (`:440-442`),
`betaCriticalHitFormula` (`:444-448`) and `blockFallDamageReductionEnabled` (`:541-543`). Every one of them is
`isDeclaredVersion(...) && !BEFORE_BETA_1_8.contains(...) && ...`, so an omitted version silently **gains**
Beta 1.8 mechanics: it would block with a sword, take reduced fall damage while blocking, use Beta exhaustion
costs, get the pre-1.1 golden apple, Beta hunger values, the Beta regeneration model and the Beta critical-hit
formula — in a world that predates all of them.

**Breaks if missed:** `HistoricalGameplayTweaksTest.everyGateAgreesWithItsBoundary` fails for exactly
`skeletonStrafing`, `criticalHit` and `panic`, because it derives the expectation from the registry's
chronology while the code reads this set (`HistoricalGameplayTweaksTest.java:88-95`):

```java

            for (String profile : PROFILES) {

                assertEquals(expected, HistoricalGameplayTweaks.appliesTo(gate, profile),
```

The seven rules above are **not** covered by that loop, and the tests that do cover two of them use hardcoded
lists that will not contain the new version (`BlockFallDamageBoundaryTest.java:17-38`,
`GoldenAppleBetaValuesTest.java:33-70`). Fixing the set is the only thing that makes them correct.

### Step 11 — turn the catalogue's planned row into an implemented one

**File:** `src/main/java/net/historicalexperience/version/HistoricalVersionCatalogue.java:200-255`.

Alpha 1.2.0 is already a planned target:

```java
// HistoricalVersionCatalogue.java:224
        planned(entries, Era.ALPHA, "Alpha 1.2.0", 1, 2, 0, null, null);
```

Change the last-but-two argument from `null` to the new profile id. `planned(...)` then derives the key, the
status and the note (`HistoricalVersionCatalogue.java:264-273`):

```java
        String key = representedBy != null ? representedBy : plannedKey(era, major, minor, patch);
        Status status = representedBy != null ? Status.IMPLEMENTED : Status.FUTURE;
        String note = status == Status.IMPLEMENTED ? "" : "no gameplay profile or generation recipe yet";
```

Edit the existing row — do **not** add a second `Entry`. Adding one leaves `planned_alpha_1_2_0` in place and
breaks the matrix count.

**Breaks if missed:** `HistoricalVersionCatalogueTest.noImplementedVersionIsHiddenFromTheMenu` fails
(`HistoricalVersionCatalogueTest.java:84-95`):

```java
        assertEquals(declared, catalogued,
            "every declared version must be reachable from the selector; a version that exists but cannot be "
                + "chosen is worse than one that does not exist");
```

### Adding a further revision to a live version (R1–R6)

A revision is a persisted recipe identifier, so this is the *normal* way to change generation content. Never
edit an existing revision, alias, settings preset or exclusion list.

1. **R1 — new alias.** Append a `GenerationRevision` with the next unused `revision` number, `experimental=true`,
   a non-blank `description`, and an alias that is neither the version id nor any existing alias. Follow the
   suffix convention of the family (`_content_preview_<n>`, `_cave_fix`, `_no_grass`, `_no_modern_content`).
2. **R2 — new settings preset** `settings_preset/<new alias path>.json`, even if the bytes are identical to the
   previous revision's.
3. **R3 — regenerate** `python scripts/generate-1211-world-presets.py` (writes the new world preset and
   rewrites the tag).
4. **R4 — repoint the public recipe** in `PUBLIC_RECIPES` to the new alias *only when it is the accepted
   latest* — the tag must name the version's `latestRevision()`
   (`GenerationBackport1211Test.java:53-59`), and `PUBLIC_RECIPES` is the one place that decides which recipe
   the menu exposes.
5. **R5 — new exclusion/ore constant if the content differs**; reusing the previous revision's constant is
   correct when the new revision only *adds* — but then it must be a new list built by concatenation, exactly
   as `BETA_1_7_3_WITHOUT_AQUATIC_PLANTS` was built from `BETA_1_7_3_WITH_REPLACED_ORES`
   (`HistoricalFeatureExclusions.java:178-193`).
6. **R6 — expect the append-only pins to fail and update them.** `HistoricalVersionsTest.java:144-165` asserts
   Beta 1.7.3 revisions ≤ 3 kept no exclusions and vanilla ores, and that revision 5 contains all of revision
   4's exclusions; `GenerationBackport1211Test`'s lower-bound counts move. This is the design working, not a
   defect: see `docs/REVIEW_NOTES.md:73`.

| `historical_experience:beta_1_8_1` | same | |
| `historical_experience:beta_1_9_pre_3` | `beta_<major>_<minor>_pre_<n>` | prereleases get `pre_<n>` |
| `historical_experience:release_1_0_0` | `release_<major>_<minor>_<patch>` | patch written even when 0 |
| `historical_experience:release_1_1` | `release_<major>_<minor>` | patch omitted when there is no patch — inconsistent with the line above, but frozen |
| `historical_experience:release_1_2_5`, `release_1_6_4` | `release_<major>_<minor>_<patch>` | |

For a new version: follow the majority shape (`<era>_<major>_<minor>_<patch>`), unless the planned catalogue
key already fixes it — `plannedKey` writes `historical_experience:planned_alpha_1_2_0`
(`HistoricalVersionCatalogue.java:283-293`), so `alpha_1_2_0` is the id that row is waiting for. Never rename
an existing id: the version id is a persisted gameplay-profile identifier
(`HistoricalMetadata.java:26-28`).

Revision aliases (`HistoricalVersions.java:81-230` for the hand-written families, `:496-621` for the two helpers):

| family | revision 0 | revision 1 | revision 2 | revision N |
| --- | --- | --- | --- | --- |
| Beta 1.7.3 | `beta_1_7_3` | `beta_1_7_3_content_preview_1` | `..._content_preview_2` | `..._content_preview_<N>` |
| Beta 1.8.1 | `beta_1_8_1` | `beta_1_8_1_cave_fix` | `beta_1_8_1_no_modern_content` | — |
| Release / Beta 1.9-pre-3 (`terrainOnly`) | the version id | `<id>_cave_fix` | `<id>_no_modern_content` | — |
| Alpha / Infdev (`terrainOnlyWithRules`) | the version id | `<id>_no_grass` | `<id>_no_modern_content` | — |

Two rules fall out of that table:

1. **Revision 0's alias is the version id, exactly.** It is the "frozen original declaration", it is the only
   revision allowed to collide with the id, and it must be `experimental=false`
   (`HistoricalVersion.java:66-76,128-134`). A numbered revision may not reuse the id.
2. **Revision 1 does not mean the same thing in every family.** For `terrainOnly` versions it is the cave
   fix; for the pre-Beta versions it is the grass exclusion. Aliases are names, not a shared sequence — always
   read the alias, never the number.

### What is append-only, and why

* A revision alias is the **persisted generation recipe identifier**. A world records it
  (`MetadataJson.java:28-34`), reports it as its marker (`HistoricalMarker.java:33-36`), and resolves its
  content through it (`HistoricalFeatureExclusions.java:412-415`). An alias the build stops declaring makes the
  world `Unreadable` (`docs/GUI-REDESIGN.md:51-53`).
* Therefore: never rename an alias, never re-point an alias at different settings, never edit an exclusion
  list or ore list that an existing revision references, and never edit a settings preset JSON in place.
  Change = new revision + new alias + new files.
* Simulation rules (`VersionRules`) are the opposite: they are keyed by the *version* and may change, because
  they alter what happens next rather than what a stored chunk contains
  (`HistoricalVersion.java:19-32`).

`HistoricalProfiles` states the reason exactly:

```java
// profile/HistoricalProfiles.java:26-30
 * <p>They are deliberately separate tables. One gameplay profile can be backed by more than one
 * generation revision over time, and each revision must stay independently addressable, because
 * {@link net.historicalexperience.world.metadata.HistoricalMetadata} persists the owned recipe
 * identifier a world was created with. Overwriting a single alias instead would silently
 * reinterpret existing worlds; a new revision is therefore a <b>new</b> identifier and a <b>new</b>
 * resolved profile value, never a mutation of an old one.
```

### 6.4 What no test checks (the manual checklist)

1. **The tag.** `GenerationBackport1211Test` counts tag entries but never compares the tag to the registry;
   omitting the entry leaves the version unselectable and every test green (§2 step 12).
2. **`settings_preset/*.json` content.** Only *existence* is asserted. Nothing checks that
   `chunkSettings."moderner_beta:preset"` equals the registry revision's `foundation`, so a settings file that
   inherits `moderner_beta:beta` while the registry records `moderner_beta:beta_1_8_1` generates terrain the
   metadata misdescribes, silently.
3. **The seven non-table gate rules.** `swordBlockingEnabled`, `betaExhaustionCosts`, `betaGoldenApple`,
   `betaFoodHungerValues`, `betaRegenerationModel`, `betaCriticalHitFormula` and
   `blockFallDamageReductionEnabled` are not in `HistoricalGameplayTweaksTest`'s gate table, and the two tests
   that cover them use hardcoded version lists (`BlockFallDamageBoundaryTest.java:17-27`,
   `GoldenAppleBetaValuesTest.java:35-39`).
4. **Lang keys.** No test reads `en_us.json`.
5. **The dimension type.** If a new version needs a different level envelope, nothing fails until a world is
   measured; the script's `reduced` flag is a hardcoded special case
   (`scripts/generate-1211-world-presets.py:93`).
6. **The runtime matrix's version list.** `scripts/verify-generation-1211-matrix.py:67-68` enumerates the
   versions it generates, so a new version is silently skipped by the one harness that measures saved chunks
   (`fullChunkBlockHashes`), preset application and block anachronisms in a real world.

## 7. Inconsistencies found

### 7.1 The registry is not the single declaration point it claims to be

`HistoricalVersions.java:21-25` says a version is declared once "plus the two resource files", and
`docs/VERSION_FRAMEWORK.md:11-19` says all five per-subsystem tables "are now derived from a single registry".
Three tables still enumerate version ids by hand and are **not** derived:

* `generation/HistoricalStructureRules.java:143-188` — `RULES` (`Map.ofEntries`).
* `gameplay/HistoricalGameplayTweaks.java:41-46` — `BEFORE_BETA_1_8` (`Set.of`).
* `generation/HistoricalBlockAvailability.java:60-71` — `CHRONOLOGY` (`List.of`), mirrored in
  `scripts/generate-1211-block-availability.py:27-38`.

A missed entry in the first two fails a test; a missed entry in the third fails a test *and*, until it does,
makes block judgements answer `UNKNOWN` for the version (`HistoricalBlockAvailability.java:966-970`). Any
documentation that promises "one entry plus two files" is understating the work by six of the seventeen steps
above (steps 8, 9, 10, 11, 12 and 14/15).

### 7.2 `docs/GUI-REDESIGN.md` preset counts are stale

`docs/GUI-REDESIGN.md:19-22` says "47 settings presets" and "47 matching world presets". The tree holds **38 of
each**:

```text
settings presets: 38
world presets:    38
presets carrying "moderner_beta:noise_settings": 35
```

The tag count in the same document (`:23-24`, "tags **10** of them") is correct and matches
`normal.json:1-15`.

### 7.3 `docs/TESTING.md` names Gradle tasks that no longer exist

`docs/TESTING.md:390-399` instructs `runRuntimeProbe`, `runRuntimeProbeReload` and
`probeVerdictNegativeControls`. None is defined by `build.gradle` or generated by Loom (verified with
`gradlew tasks --all`, §6.1). The same dead task name appears in
`scripts/prepare-probe-run.ps1:261`, `scripts/verify-lifecycle-controls.ps1:73`,
`scripts/verify-version-bounded.ps1:34` and `scripts/verify-all-declared-versions.ps1:36`. The working path is
`runServer -PgenerationProbe=true …`, which is what `scripts/verify-generation-1211.py:60-63` actually runs.

### 7.4 `scripts/verify-all-declared-versions.ps1` probes withdrawn versions

Its case list still includes `historical_experience:infdev_227` and `historical_experience:infdev_325`
(`scripts/verify-all-declared-versions.ps1:14-15`), which were deliberately withdrawn because they hang the
server during world creation (`HistoricalVersions.java:281-298`, `SpawnRestrictionSemanticsTest.java:139-151`).
It would also probe with a task that does not exist.

### 7.5 The catalogue's `Entry.key` javadoc contradicts `plannedKey`

`HistoricalVersionCatalogue.java:73-76` says of a future entry's key: "it is the id that version will take
when it is implemented, so later work does not have to renumber anything". `plannedKey` (`:283-293`) actually
prefixes `planned_`, so `historical_experience:planned_beta_1_9_pre_3` is *not* the id
(`historical_experience:beta_1_9_pre_3`), and the test at `:76-77` enforces the `:planned_` prefix. The key
does change on implementation, which is the behaviour the code has and the javadoc denies.

### 7.6 The catalogue's `order` is not on the registry's chronology scale

`HistoricalVersionCatalogue.Entry.order` is documented as "chronological key, **on the registry's own scale**,
so the two orderings cannot disagree" (`:78`), and `order(...)` claims the same (`:295-306`). The formulas
differ — registry `eraOffset + major*1000 + minor*100 + patch`
(`HistoricalVersions.java:44-52`) versus catalogue `era.chronologyBase() + major*10_000 + minor*100 + patch`
(and `minor*10 + patch` for Infdev, `:301-306`). The *orderings* agree; the *values* do not, e.g.
Alpha v1.1.2_01 is 400112 in the registry and 410102 in the catalogue, Infdev 20100420 is 300420 versus
300060. Anything that ever compares the two numbers (rather than sorting by them) will be wrong.

### 7.7 The shared dimension type and the presets disagree about the level envelope

`src/main/resources/data/historical_experience/dimension_type/beta_1_7_3_overworld.json:9-12` declares
`"height": 320`, `"logical_height": 320`, `"min_y": 0`, while every settings preset declares
`"height": 128, "min_y": 0` (`release_1_6_4.json:8-13`). The probe reports `generatorDepth` from the noise
settings (`server/GenerationVerification.java:181-182`) and the matrix asserts 128
(`scripts/verify-generation-1211-matrix.py:27`), so the generator's own depth is 128 while the dimension type
advertises a 320-high level. Recorded as an observed mismatch, not as a proven defect.

### 7.8 Pre-Beta cave biomes are still the null provider

The registry's own comment says the `moderner_beta:none` cave provider "returns a null biome" and that
revisions were added to replace it (`HistoricalVersions.java:115-120`, `:595-599`). All three Alpha settings
presets and all three Infdev presets still use it (`alpha.json:18-21`, `alpha_no_grass.json:18-21`), and
`GenerationBackport1211Test.betaLatestCaveSettingsKeepTheOriginalNonModernFallback` pins that as intentional
for `beta_1_7_3_content_preview_9` (`:139-144`). `docs/TESTING.md:5` records the scope decision ("Alpha and the
Infdev builds are untouched"). So the code and the tests agree, but the registry comment reads as if the fix
were universal. Treat it as a known content gap for the pre-Beta versions.
